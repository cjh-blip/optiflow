# 照度口径对账：算法 657 lx vs DIALux 1187 lx 那 1.8 倍

> 结论先给：**那 1.8 倍不成立。** 不是算法算错了，是拿 DIALux 的 A 灯读数去比流明法的 B 灯口径。
> 同口径的正确对比是 **657 vs 714 lx，差 8.7%**，属于配光与利用系数差异的正常范围。
> 本文逐条列证据与剩余待核项，供明天开 DIALux 时按清单核对。

## 0. 一句话链条

| 数字 | 来源 | 灯 | 光通量 | 性质 |
|---|---|---|---|---|
| **1187 lx** | 10-05 上午，NVC 雷士 `NPTLED351`（临时验证灯） | NVC | 未知 | 工作面读数，**非本链末态** |
| **714 lx / U₀ 0.66** | 10-06 与 10-11 交付报告，OPPLE 官方条目 | OPPLE `LEDPanelReC-S-Re295-30W` | 3500 lm | **维持平均照度 Ē** |
| **657 lx** | 流明法，36 盏 | 按 OPPLE 口径 3500 lm | 3500 lm | 算法预测 |

`714 / 657 = 1.087`（8.7% 差）。`1187 / 657 = 1.807`（1.8 倍）—— **那个 1.8 是拿 NVC 的读数比 OPPLE 的算法结果算出来的**。

而且 **10-06 的执行日志自己已经勘误过这件事**：

> `执行日志_20261006_SOP复跑.md:47`
> SOP 声称基线「工作面照度 1187 lx / U0 0.67」= **10-05 上午 NPTLED351（临时验证灯）时代的读数**，非本链末态（Opple 官方条目）的数值。
> 本链（STF→Opple）正确基线 = **714 lx / 0.68**。

那份日志把 U₀ 记成 0.68，10-11 的交付规范记 0.66，两者差 0.02，属版本漂移，见第 4 节待核项。

## 1. 流明法这次用到的每一个参数

以「36 盏、3500 lm、657 lx」这组为准（用户给的对照口径）。

| 参数 | 值 | 出处 | 性质 |

| 单灯光通量 Φ | 3500 lm（对照口径）；引擎默认回落 3000 lm | OPPLE 产品数据表：`03_同源链打通/交付_报告规范_20261011.md:29`「P 30.0 W；Φ光源=Φ灯具 3500 lm；η 100%」；引擎 `_task_from_ir` 里 `flux=float(b.get("flux") or 3000.0)` | 3500 是**产品数据**，3000 是**引擎默认假定** |

| 维护系数 MF | 0.80 | `engine.DEFAULT_MAINTENANCE_FACTOR` | **假定**（常量，没有来源标注） |
| 房间面积 A | 97.66 m² | 解析器对 `WALLRING_000` 闭合轮廓的鞋带公式 | **算的** |

| 盏数 N | 36 | 布灯结果（网格 + 轮廓筛除 + 补灯），非流明法反推的名义值 | **算的** |

照度公式与手算核对：

```
E = N × Φ × UF × MF / A
  = 36 × 3500 × 0.6365 × 0.80 / 97.66
  = 126000 × 0.6365 × 0.80 / 97.66
  = 64159.2 / 97.66
  = 657.0 lx        ← 与用户给的 657 完全吻合
```

**这条核对很关键**：它证明「657 lx」这个数本身没算错，公式、参数、量纲都对。问题只在拿它跟谁比。

## 3. 逐项对比：每项对 1.8 倍能贡献多少

基准：算法 657 lx（3500 lm / 36 盏 / H 4.0 / wp 0.75 / MF 0.8）vs DIALux 714 lx（3500 lm / 36 盏 / H≈3.0 / wp 0.85 / MF 未知）。

| 项 | 算法 | DIALux | 差异方向 | 对 657→714 的贡献估计 | 判定 |
|---|---|---|---|---|---|
| 光通量 Φ | 3500 lm | 3500 lm | 无 | **0** | **同口径，不是它** ✓ |
| 维护系数 MF | 0.80 | 未知 | 若 DIALux 用 0.8 → 0 | 0（若一致）；若 DIALux 用 1.0 → 算法偏低 20% | **待核，但即便差也最多 25%** |
| 有效高度 H−wp | 4.0−0.75 = 3.25 m | ≈3.0−0.85 = 2.15 m | **算法离灯更远** | 算法应**偏低**。室形指数 1.555 → 更高（约 2.3），UF 随之升高 | **可能贡献 5~15%，方向是「算法偏低」**（与观察方向一致） |
| 利用系数 UF | 0.6365（k=1.555, ρc .7/.5） | 由 DIALux 按真实反射率与室形算 | 若 DIALux 的实际反射率更高或室形更好，UF 更大 | 若真实 UF 为 0.70，则 657→722，**正好补平** | **最可能的单一大项** |
| 房间面积 | 97.66 | 97.66 | 无 | 0 | 同源 ✓ |
| 读数性质 | 平均照度 | 维持平均照度 Ē | 无 | 0 | **都是平均，不是某点值** ✓ |
| 灯具配光 | 无（流明法不含配光） | OPPLE 真实 IES | 流明法假设朗伯均匀，真实面板有配光分布 | ±10~20%（可正可负） | **系统性误差来源，但不是 1.8 倍** |
| 1187 那个数 | — | NVC `NPTLED351` | **不同灯具** | 1.8 倍的**全部来源** | **这就是那 1.8 倍的真正出处** |

### 那条 6429 不能当证据用

`执行日志_20261006_SOP复跑.md:48` 写着：

> 光通量核对：3500×36 vs **6429**×36 ≈ 0.544，实测比值 714/1187=0.601（差异=配光/利用系数），解释成立。

**这两句互相矛盾。** 若 6429 是 OPPLE 的单灯光通量，则 OPPLE 光更多，照度应**更高**，而实测 714 **低于** 1187。光通量多 1.84 倍却暗 0.6 倍，配光要背 3 倍——不可能。

而 `交付_报告规范_20261011.md:29` 明确写 OPPLE 是 **3500 lm**。

所以 **6429 这个数没有出处，且与产品数据表冲突，不能作为解释依据**。「解释成立」这个判断当时下早了。

## 4. 三个最可能的解释（按可能性排序）

### 第一：1187 是另一盏灯（NVC NPTLED351）的读数，被误当成本链基线

**可能性：最高。已有书面勘误支持，几乎可定。**

- 10-05 上午换的是 NVC，11:56 那次才是 OPPLE（同一份日志两个时间点）
- 10-06 日志明确勘误：「1187 是 NPTLED351 时代的读数，非本链末态」
- 一旦换成 714，比值从 1.81 掉到 1.09

**怎么验证（明天开 DIALux，不需要真算）：**
1. 打开 `dialux-d90a5afe.evo`，读灯具型号。若是 OPPLE → 复算应出 714 量级；若是 NVC → 这个文件就是那次的
2. 打开 `dialux-d90a5afe_run3.evo`（10-06 复跑产物），读工作面行 → 应得 **714 lx / U₀ 0.68**
3. 若两个 evo 都对上 714，**1187 这条从对照里彻底删掉**，1.8 倍命题注销

### 第二：有效高度与反射率不同，导致 UF 被低估

**可能性：中。能解释 8.7%，解释不了 1.8 倍。**

- 算法用 H=4.0、wp=0.75、ρc=0.7/ρw=0.5；DIALux 那次工作面 0.85、灯具在 z≈3.0
- 有效高度 3.25 m vs 2.15 m，室形指数差 1.5 倍左右
- UF 从 0.6365 提到 0.70 就能把 657 顶到 722，与 714 只差 1%

**怎么验证：**
1. DIALux 里读「维护系数」与三个反射率，记下实际值
2. 用同样的 H/wp/ρ 跑一次我们自己的 `uf_lookup`，看算出的 UF 是多少
3. 若 UF 落到 0.68~0.72，这条成立

### 第三：流明法的均匀朗伯假设 vs OPPLE 真实配光

**可能性：中低。属于系统性偏差，量级 10~20%，且方向不定。**

- 流明法把整灯当各向均匀发光，真实面板灯有 IES 配光
- 直下式面板的近场分布比朗伯更集中，工作面可能偏高；但有遮挡与反射损失，也可能偏低
- 这条**解释了那 8.7%，但方向可能是反的**（算法偏低 8.7% 也可能是 UF 高估）

**怎么验证：**
1. 拿 OPPLE 的 IES 与朗伯分布做对比，看半峰角与光通量分布
2. 若有条件，用 IES 做一次逐点积分（不需要 DIALux），与 657 对比
3. 若积分结果接近 714，说明配光是主因；若接近 657，说明 UF 是主因
